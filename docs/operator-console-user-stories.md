# Worker 网站运维控制台：User Stories

## 产品视角修正

这个界面不是面向多租户客户的 SaaS Dashboard，也不是创建 Cron 的配置后台。它是网站所有者用于照看多个 Cloudflare Worker 网站的私人运维控制台。

在默认心智模型中：

- 一个网站由一个 Cloudflare Worker 承载；
- 一个网站 Worker 可以声明多个业务 Cron；
- Cron 配置属于网站代码和 Registration，控制台只呈现真实运行状态并提供安全干预；
- 用户通常也是这些网站的开发者和运维者，不需要销售式引导、增长指标或频繁的接入流程。

## 核心用户

**网站所有者 / 开发者 / 当值运维者**

他管理若干个由 Cloudflare Worker 搭建的网站。每个网站背后都有定时执行的业务职责，例如同步数据、刷新缓存、生成内容、发送摘要或清理过期记录。他打开控制台时通常只有两个意图：快速确认业务自动化是否正常，或定位并处理一个已经发生的异常。

## 总 User Story

> 作为同时运营多个 Cloudflare Worker 网站的网站所有者，我希望打开控制台后十秒内知道整体业务是否正常、哪个网站的哪个 Cron 需要我关注，以及下一步应查看或执行什么操作，从而在不阅读底层日志和平台术语的情况下确认业务持续运行，并安全处理异常。

## 使用节奏

### 正常状态：快速巡检

用户没有耐心浏览一套产品叙事。他只想确认：

1. 调度系统当前是否还在工作；
2. 所有网站是否都在正常执行自己的 Cron；
3. 有没有失败、结果未知、长期未运行或被阻止的任务；
4. 最近发生了什么，接下来将发生什么。

成功标准是用户扫一眼即可放心离开，而不是在多个页面之间证明“没有问题”。

### 异常状态：从业务影响进入处置

用户可能从失败记录、网站异常或外部告警来到这里。他首先需要知道受影响的网站和任务，然后理解失败性质、最近尝试、是否可能已经产生副作用，以及哪一种处置是安全的。

成功标准是用户能沿着“网站 → Cron → Execution → Attempt”逐层缩小问题，并明确选择 Retry、Run Again、人工确认结果、暂停任务或停用网站 Worker。

## 各功能的用户动机

### 1. 业务总览

**User Story**

> 作为网站所有者，我希望首页直接告诉我所有网站的业务自动化是否正常，并把需要处理的问题排在最前面，以便我不用理解控制平面的内部结构就能决定是否需要行动。

**用户真正想回答的问题**

- 现在是否一切正常？
- 哪个网站出了问题？
- 是明确失败、结果未知、调度停滞，还是人为暂停？
- 最近有哪些重要运行结果？
- 接下来哪个 Cron 会执行？是否存在明显积压或长期未运行？

**页面存在的理由**

首页是业务状态入口和异常分流器，不是品牌展示、产品介绍或统计海报。正常时它应极快地给出“无需处理”；异常时它应把最紧急的问题和下一步入口直接暴露出来。

### 2. 网站 Workers

当前系统中的 Target、Registration 和 Registration Token 都围绕同一个网站 Worker 服务，但用户动机不同。

**User Story**

> 作为网站所有者，我希望看到每个网站 Worker 当前是否在线、声明了哪些 Cron、最近何时发布配置，以及是否被平台阻止，从而判断问题属于某个网站、它的配置，还是统一调度平台。

**用户真正想回答的问题**

- 我管理的哪些网站已经连接？
- 每个网站有几个 Cron，哪些正常、哪些异常？
- 网站 Worker 最近一次 Registration 是否成功，当前运行的是否是预期版本？
- 网站整体是否被停用，Service Binding 是否可达？

**功能动机判断**

- Target 是网站 Worker 的物理身份，但不应作为用户必须先理解的平台术语。
- Registration 是网站发布 Cron 配置的证据，适合作为网站详情中的版本与同步状态。
- Token 签发、轮换和撤销是低频维护动作，应位于网站接入或安全设置中，而不是与日常巡检功能争夺一级注意力。

### 3. Cron 计划

**User Story**

> 作为网站所有者，我希望按网站查看它声明的所有 Cron，并快速比较每项任务的职责、运行频率、最近结果、下一次运行和阻塞原因，从而确认业务任务没有遗漏、停滞或在错误时间执行。

**用户真正想回答的问题**

- 这个网站有哪些自动任务？每个任务做什么？
- 上次运行是否成功，下次什么时候运行？
- 为什么它现在不会运行？是网站声明停用、管理员暂停、网站 Worker 停用、配置失效，还是全局暂停？
- 网站维护期间，能否只暂停这个 Cron，且不被下一次部署覆盖？

**功能动机判断**

用户主要是查看和理解，不是在控制台新建或编辑 Cron。Pause / Resume 是为了临时控制业务风险，不是配置管理。

### 4. 执行与异常处理

**User Story**

> 作为处理故障的网站所有者，我希望从一次异常 Execution 看清业务意图、每次 Attempt、错误、输出和幂等风险，从而判断业务是否已经发生，并选择不会意外重复副作用的恢复动作。

**用户真正想回答的问题**

- 这次运行属于哪个网站、哪个 Cron，原本计划什么时候发生？
- 是业务明确失败，还是平台无法确认结果？
- 已经尝试了几次，每次发生了什么？
- 是否允许安全 Retry？Run Again 为什么风险更高？
- 如果业务系统已经完成，我如何人工确认并留下审计说明？

**功能动机判断**

Execution 列表的价值不是保存一张流水账，而是提供异常队列与调查入口。Attempt 时间线、结果输出和风险动作只在需要诊断时逐步展开。

### 5. 调度系统状态

**User Story**

> 作为网站所有者，我希望在所有网站同时异常时快速确认统一调度器是否仍在运行，并在风险扩散时暂停全部派发，从而区分平台故障和单个网站故障。

**用户真正想回答的问题**

- 最近一次 Tick 是否按时且成功？
- 当前是否处于全局暂停？
- 调度容量是否接近上限？
- 多个网站同时失败是否源于同一个平台问题？

**功能动机判断**

系统心跳和全局暂停很重要，但属于故障诊断与紧急控制。关键异常应在业务总览出现；完整技术信息可以留在二级系统页面。

### 6. 登录与凭据

**User Story**

> 作为唯一管理员，我希望快速、安全地进入自己的控制台，并只在网站首次接入或凭据轮换时处理 Registration Token，从而让认证保持可靠但不干扰日常运维。

**功能动机判断**

登录是进入控制台的门槛，不是产品体验的主角。Registration Token 是机器接入凭据，不是日常 API Key 管理产品。

## 任务优先级

按用户使用动机排序：

1. 判断整体是否正常，并发现需要处理的异常；
2. 定位受影响的网站 Worker 和 Cron；
3. 理解 Execution / Attempt 并安全处置；
4. 查看某个网站的全部 Cron 与近期运行；
5. 暂停单个 Cron、单个网站或全局派发；
6. 检查 Registration、Service Binding 和系统心跳；
7. 首次签发或轮换 Registration Token。

这个顺序意味着现有导航中“目标服务”“注册与凭据”“系统”不应与业务总览、网站和异常处理拥有同等视觉权重。

## 信息架构含义

后续 UI/UX 改造应优先探索以下结构，而不是直接美化现有页面：

- 以“网站 Worker”作为一级业务对象，将 Target、Registration、Actions、Cron 数量和连接状态聚合在网站上下文中；
- 业务总览首先呈现跨网站异常、整体健康、最近重要结果和即将运行的任务；
- Cron 默认在网站上下文中被理解，同时保留跨网站查看和筛选能力；
- Execution 默认服务于异常调查，完整历史是次一级需求；
- Token 与底层系统信息降级为网站设置或高级运维入口；
- 状态文案先说业务含义，再保留 Target、Execution、Attempt 等精确技术词作为证据。

## 明确反目标

- 不做多租户、套餐、增长、活跃用户或转化率式 SaaS Dashboard；
- 不用大段品牌叙事、滚动展示或装饰性指标占据业务总览；
- 不把所有实体拆成同等权重的导航和同形卡片；
- 不让用户从 Target、Registration、D1、RPC 等实现术语开始理解系统；
- 不在控制台重新提供 Worker 已拥有的 Cron 创建与编辑能力；
- 不用绿色百分比掩盖 unknown、skipped、blocked 或样本量不足。

## 本轮待确认

1. 业务总览同时服务于正常巡检和异常分流：正常时可以快速离开，异常时直接进入受影响网站或 Execution。
2. “网站 Worker”成为用户可见的一级对象；Target 和 Registration 作为其技术证据与设置存在。
3. 低频接入、安全凭据和系统细节降低导航与视觉优先级，但不删除能力。
