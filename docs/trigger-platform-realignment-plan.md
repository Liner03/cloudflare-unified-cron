实施选择见 [ADR 0003](adr/0003-independent-trigger-delivery.md)，使用方式见 [Queue 接入指南](queue-worker-integration.md)，新证据见 [2026-09-12 本地记录](test-runs/2026-09-12-local.md)。当前模式由物理 Target 配置决定：已有 Target 默认保留 RPC；新独立执行模式需显式配置 Queue，避免静默改变旧业务语义。

## 1. 用户目标

Cloudflare 只配置一个 `* * * * *` 原生 Cron Trigger。平台保存多个网站的定时规则，到期时触发对应网站 Worker。网站 Worker 拥有并执行其业务代码。允许分钟级调度，优先满足免费计划下的实际用量。

目标态中，平台应在任务被可靠接收后继续处理其他触发，不把网站业务执行完成作为本轮派发结束的条件。平台可以观察执行结果，但业务执行不应依赖平台调用一直存活。

分别度量三个数量，不混用“100 个”：

- 规则总数：例如 10 个网站共 100 条 Cron。
- 同时到期数：例如上述规则中 10 条同一分钟到期。
- 独立网站 Worker 数：例如 100 个网站各有一条规则。

首个容量目标是至少 100 条逻辑规则、多个真实网站 Worker；100 条同分钟触发作为独立压力目标。100 个独立 Worker 的账户容量与调用限制单独核验，不能由单 Worker 上的 100 条规则测试替代。

已经符合目标、应保留的部分：一个原生分钟 Trigger、D1 保存规则、业务代码位于网站 Worker、声明式 Registration、同一 occurrence 去重、权限边界、暂停开关、审计与 UI。

等待 RPC 结果并不等于业务在平台内执行，也不是只能派发 2 个的理由。现有实现可以并发调用；它的不足是容量保护未经需求验证，以及任务生命周期没有完全解耦。

## 3. 架构决定

目标流程：一个原生 Cron → D1 到期触发记录 → 可靠投递 → 对应网站 Worker 执行业务 → 可选结果回报。

保留当前同步 RPC 作为兼容模式，先解决多网站与容量问题。新触发模式通过单独的传输适配器实现，避免直接改坏现有 Execution/Attempt 的结果语义。

可靠投递的首选验证方案是 Cloudflare Queues：平台把任务写入目标网站对应的 Queue；网站 Worker 的 `queue()` handler 调用自身业务函数。Queue 唤醒消费者，不为网站增加原生 Cron Trigger。Queue 返回已持久接收后，平台可以结束本次投递；消费者完成业务后才确认消息。不同网站的队列与消费并发隔离，避免一个慢站点拖住其他网站。

这需要额外 Queue 绑定和消费者配置，必须先验证接入成本与免费用量再作为默认模式。若现有网站已经有可靠队列/执行设施，可实现同等语义的接收接口复用它；只在 D1 写入 inbox 而没有可靠唤醒机制，不算完成交付。

如果免费用量和低接入成本更适合保留直接 RPC，则明确其仍是等待完成的兼容模式，不把它宣传成完全独立执行。两者区别在文档和 UI 中可见。

不能用以下做法替代可靠执行：删除 `await`、无持久化的立即 200、仅依靠内存中的 Promise、用 `waitUntil()` 假定业务可以无限后台运行。

## 4. 实施顺序

### 第一步：先验证免费额度和独立执行方式

编写最小多 Worker 原型，对比现有直接 RPC 与 Queue 投递。记录平台 CPU、业务 Worker CPU、RPC/投递调用次数、D1 statements/rows、Queue 操作量与实际触发延迟。

验证调用方结束或重启后，已接受的任务仍能完成；接收前失败可重投；接收后丢失响应不会重复业务副作用。引入 Queue 时，在网站 Worker 内执行实际业务，不把业务搬回平台。

输出一份 ADR：决定新触发模式的交付机制、免费计划适用用量、接入资源和生命周期边界。该步骤决定传输实现，不能仅将常量从 2 改成 100 后声称支持。

### 第二步：补齐真实多网站接入

用一份 Target 配置生成/校验 manifest、Wrangler bindings、类型和 D1 sync 数据，消除四处手工同步和 `CRON_DATA` 特例。

只允许部署者预授权的 Target；Registration Token 仍不能自建信任、任意指定 URL 或其他网站的队列。缺少绑定、绑定类型不符、Action 版本不符应在接入检查时明确报错。

至少用三个独立 Worker 验证路由和隔离。为网站提供复用业务函数的 SDK 示例：原 `scheduled()` 和新入口调用同一业务函数，但迁移结束后只保留一个启用的触发来源。

### 第三步：重构到期扫描和容量约束

统一规则总数配置，首先支持配置为 100。区分单份 Registration 数量、全局规则数量、Target 数量、入站 64 KiB 与 payload 大小，不能扩大其中一项却暗中被另一项截断。

数据库容量限制使用新 migration 更新，保留事务级并发约束；不改写已应用的历史 migrations。降低配置低于现有数量时禁止新增，不能删除已注册规则。

Tick 采用有界分页与小批量事务，原子保存 occurrence 与推进 nextRunAt；分页不能使用会因更新排序字段而漏项的 offset。任务启动/投递并发单独控制，槽位释放后继续调度；设全局和每 Target 预算，重投与新触发公平分配。

减少每条规则重复读取 capability 的开销，复用单 Tick 内的已校验数据；涉及 Token 撤销、Target 禁用、claim 的安全条件仍需数据库守卫。批量 SQL 受参数/statement 限制约束，避免无界大事务。

达到本轮预算时保留明确积压并记录 lag；不得为了让计数变小静默吞掉触发。宕机补触发、coalesce、skip 与重叠是单独策略，保持可见、可解释。

### 第四步：拆分投递状态和业务状态

新协议分别记录：待投递、投递结果未知、已可靠接收，以及可选业务 running/succeeded/failed。Queue 已接收只能算已入队，不代表目标 Worker 已开始或业务已成功。

Occurrence 的稳定 identity 沿用 Schedule ID + scheduledFor；网络重投保持同一 identity。发送前持久化 outbox/投递意图，发送成功但记录失败时允许重投，执行端用稳定 identity 保证幂等。

平台只重试投递层故障；业务重试由执行端策略负责，不能平台与 Queue 双重重试放大副作用。非幂等 Action 的自动重投必须有接收端去重/业务安全证明，不因接收成功就推断 exactly-once。

完成回报使用专用、绑定 Target 的权限与结果接口，不能复用 Registration write Token 的权限。回报需幂等、身份匹配，迟到结果不能覆盖新尝试；回报失败不触发业务重跑。

在新模式下，业务结果未知默认不应自动阻塞未来分钟触发；是否允许业务重叠由显式策略管理。旧同步模式保留原安全默认值，迁移时不悄悄改变。

暂停应分别说明“停止未来触发”和“执行端暂停消费”。已经交付的消息不能靠平台暂停或 Cancel 假装撤回；网站停用、Queue 消费和在途任务的处理需明确演练。

### 第五步：迁移原生 Cron 与调整控制台

增加 Cron 方言标识与迁移预览；旧声明缺省仍使用现有 Unix 方言。Cloudflare 来源的数字星期明确转换，无法安全转换的扩展表达式明确拒绝并提供修改建议。用未来发生时间比对，避免只验证字符串格式。

接入说明分为“共享原业务函数”“接入新的触发入口”“验证测试规则”“关闭旧原生 Trigger”“启用平台规则”。原生 Trigger 的移除由网站部署流程明确执行，考虑传播窗口与切换去重，防止双重触发。

控制台以网站、规则、下一次触发、已投递/投递失败/积压为主。业务成功率和业务重试作为可选扩展；未收到业务结果应显示未知/未上报，而非成功。

### 第六步：按真实使用目标重新验证

实施前将新增和受影响场景合并进 [唯一测试清单](test-plan.md)，沿用其 ID 规则、证据模板、阶段顺序和已批准的 60 分钟观察要求。本文是修复设计，不另建第二份测试清单；旧报告保持历史事实，新实现不继承旧 PASS。

需要加入清单的验收场景：

- 10 个网站各多条规则，精确投递到对应 Worker，跨站 Token/绑定请求被拒绝。
- 100 条规则可以注册和显示；同时到期 10/25/50/100 条分别记录完整性、触发延迟、quota、CPU 和数据库用量。
- 100 条同一分钟触发与 100 条每分钟持续触发分别测量；后者未通过前不得宣称“100/min 稳定”。
- 建议目标：轻量接收端的同批任务在本次真实 Tick 启动后 60 秒内全部可靠接收；原生 Trigger 自身延迟单独报告。最终默认预算由此数据决定。
- 单站故意慢于 30 秒或失败，其余站点仍能被及时触发；可靠接收后平台重启，网站业务仍能完成。
- 重复 Tick、重复投递、接收后响应丢失、回报丢失、消费者重启均不产生重复业务副作用。
- 原生 Cron 的日期转换、暂停/恢复、旧新入口切换、旧协议回滚均有证据。

先本地完成实现和上述故障验证，再按用户的 Cloudflare 身份及资源授权门禁安排有限 Staging 验证。已删除的测试资源不会因本文自动重建；无需为了容量测试部署 100 个真实 Worker。

## 5. 免费计划的约束与选择依据

官方 [Service bindings 限制](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/#limits) 说明单请求最多涉及 32 次 Worker 调用，且调用计入 subrequest。因而“一次 Tick 直接 RPC 100 个网站”不能作为默认可行方案；给同一个调用链多加几层转发也不能假定刷新配额。

[RPC 生命周期](https://developers.cloudflare.com/workers/runtime-apis/rpc/lifecycle/) 说明调用方上下文结束会影响下游上下文。可靠接收机制需要真正独立的消费触发。

[Workers limits](https://developers.cloudflare.com/workers/platform/limits/) 与 [Queue pricing](https://developers.cloudflare.com/queues/platform/pricing/) 都要纳入原型预算。Queues 可在 Free 使用，但有每日操作额度。按当前文档正常消息通常约 3 次操作，100 条每分钟持续投递约 432,000 次操作/天，不能据此承诺完全落在免费 Queue 额度内。100 条每小时约 7,200 次操作/天，还需计入重试及同账户其他用量。以上是用量估算，不是容量测试结果；实施时重新核对官方配额。

不把付费设成部署前提。先给出“规则数 + 执行频率 + 同时到期数 + 业务成本”的免费可运行范围；若免费配额无法覆盖具体负载，明确给出限制与备选方案，不以取消安全检查换取表面吞吐。

## 6. 完成定义与交付

交付包括：架构 ADR、多 Target 接入生成/校验工具、可配置容量与有界批处理、可靠投递协议和网站执行适配、迁移指南、区分投递/业务状态的 UI，以及唯一测试清单的新证据报告。

最终对外承诺应是“一个原生 Trigger 管理至少 100 条已验证的逻辑规则，业务在网站 Worker 执行；明确列出免费计划验证过的触发负载与时延”。100 个不同网站、100 次每分钟持续执行、完全独立执行分别需要对应证据，不以规则数替代。
